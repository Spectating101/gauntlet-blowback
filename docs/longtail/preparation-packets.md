# Preparation Packets

The purpose of this document is to make the 2nd, 20th and 50th campaign materially cheaper than the first.

## 1. Canonical person / applicant packet

Prepare once and keep current:

- legal name and preferred English name;
- current YZU program, department, degree level and expected graduation date;
- enrollment-status proof and student ID copy where safe/required;
- nationality / residency / work-authorization facts needed for eligibility checks;
- English CV master;
- 100-word, 250-word and 500-word biography;
- headshot only where explicitly required;
- contact email / phone;
- GitHub / portfolio / LinkedIn or other public professional links actually maintained;
- transcript / GPA / ranking only when required;
- advisor / professor contact only when a real endorsement or host is required;
- bank/payment information only at award/payment stage, never embedded in general dossiers.

Private personal facts should not be copied into broad reusable packets. Blowback should represent them as boolean/typed eligibility facts and ask for them only when necessary.

## 2. Canonical project packet — common schema

Every active project should have the following reusable components:

### Identity
- canonical project name;
- one-line description;
- 50-word description;
- 150-word description;
- target user / beneficiary;
- problem statement;
- current maturity state.

### Evidence
- canonical repository / release / deployment URL;
- latest authoritative commit/release candidate;
- tests / validation counts that are safe and current;
- screenshots / demo video / architecture diagram;
- external usage / professor / partner / reviewer evidence, if any;
- claim ledger: `PROVEN`, `INFERRED`, `UNPROVEN`;
- explicit limitations / remaining blockers.

### Conversion narratives
Generate reusable 200–500 word variants for:

- research / academic merit;
- AI / engineering innovation;
- public-good / social impact;
- industrial / commercial value;
- open-source / infrastructure value;
- policy / governance value;
- education / university value.

These are translations of the same evidence, not new claims.

### Deliverables
- 1-page project summary;
- 2-page proposal shell;
- 5-slide lightning deck;
- 10-slide competition/pilot deck;
- architecture figure;
- 1–3 minute demo script;
- 100/250/500-word abstract variants;
- budget template for NT$5k / NT$20k / US$1k / US$3k asks;
- simple milestone plan for 2 weeks / 1 month / 3 months;
- IP / licensing statement;
- data/privacy/ethics statement where relevant.

## 3. Project-specific packet gaps

### Cite-Agent
Must have:
- canonical controlled-beta description;
- latest release candidate and deployment link;
- researcher journey screenshots;
- evidence/coverage/citation-verification capabilities stated conservatively;
- data/privacy statement;
- beta/pilot ask template;
- lab deployment/support scope;
- 2-week and 4-week paid evaluation packages;
- research-tool / education-AI / agent-AI competition narratives.

Do not claim broad production maturity before real beta evidence supports it.

### YZU / Research Drive
Must have:
- institutional research-workflow problem statement;
- exact frontend/backend release identity once promoted;
- live host proof;
- professor/researcher workflow screenshots;
- separation between YZU-specific deployment and reusable research-infrastructure expertise;
- institutional diagnostic service narrative;
- education AI / data infrastructure / research platform competition narrative.

Do not sell a clone of YZU before the real host has completed handoff/adoption.

### Policy Lab
Must have:
- empirical/evidence-governance thesis;
- portfolio of validated analyses / policy problems;
- reproducibility / evidence-integrity statement;
- competition abstract variants for governance AI, public policy, open data, finance;
- paid evaluation-sprint scope;
- 1-page client memo sample structure;
- conference / paper / fellowship packet.

### Nocturnal Oversight
Must have:
- engineering-frozen state and public/intake/operator architecture;
- synthetic-pilot validation and its limitations;
- cold-review packet;
- 1-page public-memory/accountability use-case dossier;
- newsroom/watchdog/civic-research pilot scope;
- bounded monitoring pilot price/scope template;
- security/privacy claims kept separate from aspirations.

### Hardware Splicer
Must have:
- authoritative frozen-head state;
- explicit statement that no demonstrated software blocker remains, while live-unseen / physical evidence boundaries remain where applicable;
- architecture / CV / electronics verification diagrams;
- benchmark/test evidence;
- 1–3 minute demo;
- industrial PoC scope: one inspection problem, input, output, success criteria, evidence artifact;
- competition variants for semiconductor, automation, machine vision, AI agent, safety;
- design-partner one-pager.

Do not convert a prize into an excuse for a new derivative hardware product.

### Public-Good Control
Must have:
- current generalized coordination/control-plane framing;
- one concrete beneficiary/operator problem per campaign;
- evidence-integrity / stale-opportunity fail-closed behavior;
- shadow-pilot plan;
- public-good/climate/civic variant;
- small-grant budget variants where US$500–1,000 actually triggers a bounded action;
- partner qualification checklist.

### Refinery / Commons
Must have:
- Capability -> Implementation -> Claim/evidence model;
- demand-observatory evidence with clear non-claims;
- heterogeneous-case validation summary;
- OSS maintainer audit example;
- evidence-audit paid service shell;
- OSS/open-infrastructure/research-software grant narrative.

### Sharpe Terminus
Must have:
- conservative causal/research-engineering description;
- forward-paper / risk-control architecture;
- no-performance-guarantee statement;
- reproducibility / research-pipeline audit service shell;
- finance/data/quant job narrative;
- research-paper / method competition narrative.

Never market unproven alpha.

### Research papers / thesis line
Must have:
- canonical paper list with status, venue and latest version;
- 100/250/500-word abstracts;
- contribution / method / results / limitations summaries;
- reproducibility package links;
- poster template;
- conference-short-paper template;
- policy relevance note;
- award/prize eligibility notes, including prior-publication constraints.

### Citation Engine
Must have:
- neutral evidence/authority kernel description;
- current integrations and what each actually proved;
- open-source license / public repo state;
- architecture / API / MCP integration diagram;
- verifiability / provenance / agent-governance narrative;
- maintainer identity packet for OSS credit/funding programs;
- paid integration-review scope.

## 4. Submission-specific reusable templates

### 500-character money-use statement
Structure:
1. exact bounded action;
2. direct cost items;
3. measurable output within 2–8 weeks;
4. what exists already, so funding is catalytic rather than speculative.

### 2-page microgrant proposal
1. problem / beneficiary;
2. what already exists;
3. exact funded activity;
4. milestones;
5. budget;
6. evidence and limitations;
7. public/open output if applicable.

### Competition abstract
1. problem;
2. existing solution;
3. technical distinction;
4. evidence;
5. intended user / application;
6. limitations and next validation.

### Paid pilot one-pager
1. target pain;
2. bounded pilot scope;
3. customer inputs;
4. deliverables;
5. acceptance criteria;
6. timeline;
7. test price;
8. data/privacy/IP terms;
9. next-step options.

## 5. Before every FIRE

Blowback must answer:

1. Is the organizer/source real and current?
2. Is the applicant vehicle eligible?
3. Can the project be submitted mostly as it exists now?
4. Are there duplicate/category limits across related campaigns?
5. Are all claims supported by current evidence?
6. What is the actual marginal human work?
7. What is the smallest cash-bearing outcome?
8. What is the result latency?
9. Is there a reimbursement/credit/secondary stack after submission?
10. What exact receipt proves the shot was fired?

If any answer materially changes the economics, recompute priority before submission.
