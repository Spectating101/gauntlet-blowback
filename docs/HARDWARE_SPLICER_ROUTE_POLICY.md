# Hardware-Splicer Route Policy

Blowback should optimize for repeated external verdicts with low marginal work **without treating route allocation as project amputation**.

Current rebalance overlay:

- `docs/HARDWARE_SPLICER_REBALANCE_2026-09-23.md`
- `data/hs-route-rebalance-2026-09-23.json`

For Hardware-Splicer specifically:

- preserve Hardware-Splicer as a first-class flagship technical asset;
- prefer routes where physical agents, hardware evidence, EDA/release assurance, embodied systems or consequential authority are native to the opportunity;
- reallocate a route when another portfolio asset is clearly more native or requires materially less marginal work, but preserve the historical HS packet and allow later reassignment if evidence changes;
- treat competitor progress as an input to targeted improvement, not as a reason to dismantle HS;
- allow bounded engineering when a competitor exposes a concrete gap inside HS's native lane, a live route becomes materially more winnable, an evaluator/user/provider exposes a defect, or the product shell can be improved without weakening frozen evidence semantics;
- prefer integration/adapters when a competitor or source tool already owns the underlying editing, transport or generic infrastructure capability;
- prefer solo-compatible competitions and academic routes;
- preserve adviser-only routes when the upside is meaningful;
- kill routes that require recruiting peer teammates solely for eligibility;
- keep every opportunity in `inspect` mode until the live form map is verified;
- use the canonical Hardware-Splicer submission package as upstream truth;
- never upgrade software/MCP evidence into physical proof;
- never infer legal eligibility or attest originality/authorship in-browser;
- never autonomously click final submit.

## Engineering allocation rule

Generic feature expansion is off by default, but HS is **not** frozen against genuine competitive improvement.

Before opening an engineering tranche, ask:

1. What specific competitor/user/evaluator/evidence gap does this close?
2. Is the gap inside HS's native physical-agent / evidence / release-assurance lane?
3. Does fixing it improve a live route, external proof, interoperability, research contribution or user comprehension?
4. Should HS own it, or integrate the stronger external/source-tool capability?
5. Can it land without weakening exact revision, evidence validity and authority boundaries?

If the answers support action, improve HS. If not, fire the existing package or allocate the route elsewhere.

The conversion objective is to make submissions mostly clerical projections of existing evidence **while continuing to strengthen HS when evidence and competition justify the work**.
